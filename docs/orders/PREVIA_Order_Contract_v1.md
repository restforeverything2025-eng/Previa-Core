# PREVIA — Order Contract v1

**Project:** PREVIA  
**Domain:** Order / Purchase  
**Status:** APPROVED  
**Purpose:** Minimal contract for the first real Order implementation in Previa-Core.

## 1. Order entity

The Order represents one purchase attempt and its lifecycle.

Fields:

- `order_id` — unique order identifier, generated by the system.
- `created_at` — creation timestamp, generated by the system.
- `source` — origin of the order, e.g. `telegram`.
- `customerId` — PREVIA Customer ID; nullable for Guest Orders.
- `provider` — external identity provider, e.g. `telegram`.
- `providerId` — provider-side user identifier; required for the current Telegram flow.
- `telegram_username` — Telegram username snapshot; nullable.
- `telegram_name` — Telegram display-name snapshot; nullable.
- `customer_name` — customer name used for this order; required; stored as an order snapshot.
- `phone` — customer phone for this order; required.
- `email` — customer email for this order; required.
- `payment_type` — payment scenario/type.
- `payment_method` — concrete payment method.
- `payment_status` — payment lifecycle state.
- `order_status` — order lifecycle state.
- `subtotal` — sum of order items before additional adjustments.
- `total` — final order amount.
- `expires_at` — reservation/payment deadline; nullable when not applicable.
- `paid_at` — confirmed payment timestamp; nullable until payment.
- `document_url` — generated order document reference; nullable.
- `note` — optional order note.

## 2. OrderItem entity

`OrderItem` represents a product captured in a specific order.

Fields:

- `order_id` — parent Order identifier.
- `sku` — product SKU.
- `title` — product title snapshot.
- `price` — unit price snapshot.
- `quantity` — quantity ordered.
- `subtotal` — line subtotal.

## 3. Guest Orders

A customer does **not** need a PREVIA `customerId` to purchase.

For a Guest Order:

- `customerId` is empty/null.
- `provider` and `providerId` identify the external user.
- The order remains valid and can later be associated with a PREVIA Customer if a Customer profile is created.

## 4. Identity rules

`providerId` is the external identity reference and is not replaced by `customerId`.

`customerId` is PREVIA's internal Customer reference and may be absent at order creation.

`telegram_username` and `telegram_name` are snapshots for the order, not primary identifiers.

## 5. Separation of responsibilities

- **Previa-Core:** Order domain rules, validation, totals, lifecycle and reservation logic.
- **Previa-CMS:** persistence adapter/infrastructure for Google Sheets.
- **Google Sheets:** storage of `Orders` and `OrderItems`; it does not own business rules.
- **Telegram/App:** presentation and collection of client input.

## 6. Initial purchase flow

`Product → Buy → availability check → customer form → Order creation → reservation → payment → result to customer`

This contract is intentionally limited to the first Order implementation. Additional concerns such as notifications, document generation and advanced payment integrations are separate services and are not expanded here.

## 7. Approved implementation principle

**Contract first → implementation → test → user approval → next change.**

No repository changes, deployment or production migration are implied by this document.
